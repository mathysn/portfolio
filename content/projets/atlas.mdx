## Le contexte

Les équipes planifiaient les tournées sur des tableurs partagés. Objectif : un outil unique, [synchronisé en temps réel](#architecture), utilisable depuis le dépôt comme depuis la route.

<Callout type="info" title="Bon à savoir">Les données de démonstration sont régénérées chaque nuit.</Callout>

### Contraintes techniques

- Ingestion de `12 000` positions GPS par minute
- Mode hors-ligne complet pour les chauffeurs
- Migration progressive, sans interruption de service

> Le temps passé à planifier a été divisé par trois dès le premier trimestre.

## Architecture

Le front Next.js consomme une API NestJS découpée en modules métier (flotte, tournées, facturation). Les positions GPS transitent par une file SQS avant d'être agrégées dans PostgreSQL, ce qui absorbe les pics sans ralentir l'interface.

La route qui alimente la carte reste volontairement simple : elle ne renvoie que les véhicules actifs et leur dernière position connue.

```ts title="app/api/vehicles/route.ts" {5}
import { db } from "@/lib/db";

export async function GET(req: Request) {
  const fleet = await db.vehicle.findMany({
    where: { active: true },
    select: { id: true, position: true },
  });
  return Response.json(fleet);
}
```

<Callout type="warning" title="Attention">L'API publique est limitée à 100 requêtes par minute.</Callout>
